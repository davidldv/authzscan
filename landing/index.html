Access-control bugs are rarely a missing login. They're a logged-in user reaching another user's row, and the broken version is a near-copy of the correct one. That's why pattern matchers struggle: there is no bad syntax to match on.

scoped 
const invoice = await db.invoice.findFirst({
  where: {
    id: params.id,
    userId: session.user.id
  }
})
not scoped 
const invoice = await db.invoice.findUnique({
  where: {
    id: params.id
  }
})

One extra line, and it answers a question no linter asks: whose row does this return? Answering it means following params.id from the request, through every helper it touches, down to the query. That is reasoning about the program rather than scanning it.

Four passes. Only two of them ask a model anything.

Enumeration is a solved problem, so it stays deterministic. The model gets spent only where judgement is genuinely required, and then it has to argue against its own findings.

01Inventory

Walk the AST for every route handler and Server Action, detect the auth library, and pull out the ownership idioms the repo already uses.

ts-morph

02Trace

Follow each client-controlled identifier (route param, body field, query string) to the database call it reaches, and flag any call with nothing scoping it to the caller.

claude

03Verify

Re-read the cited code adversarially and throw the finding out unless a concrete "user A reaches user B's resource" path survives.

claude

04Render

Markdown, SARIF 2.1.0 for GitHub code scanning, or JSON, plus an exit code you can gate a build on.

deterministic

Every cell resolves to one of four things, and one of them is "I couldn't tell"

scoped

The query is bound to the caller. Nothing to report.

not scoped

A concrete path where one user reaches another's object. Cited to file and line.

unverified

A candidate the verify pass couldn't confirm. Surfaced at low confidence rather than quietly dropped.

not analyzed

The endpoint was reached but couldn't be followed. Reported as unanalyzed, never as clean.

That last state is the one that matters. A scanner that turns "I ran out of budget" into a green check is worse than no scanner, because someone will believe it.

What the number doesn't cover: it's one run, not a mean across many, so there's no error bar on it yet. It was measured on Sonnet 4.6 and would move on another model. Two of the 17 confirmed findings landed on the same planted bug, because a route handler and its Server Action live in one file, so the run confirmed 16 distinct bugs rather than 17. And a benchmark somebody wrote on purpose is easier than a codebase that grew by accident. I pointed it at a real one and wrote down what the perfect score failed to predict.

The harness gets checked separately. An oracle that reads the answer key straight out of the manifest has to score a perfect 1.0 / 1.0, which proves the scoring is right no matter how the model performs.

Scope is deliberately narrow: object-level authorization in App Router route handlers and Server Actions. Not XSS, not SQLi, not login flaws, not the Pages Router. One class of bug, done properly.
